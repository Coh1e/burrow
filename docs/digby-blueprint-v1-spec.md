# Digby 与 Blueprint 首版

## Problem Statement

团队要在 Windows、Linux 和 macOS 上复用同一套构建流程。一次流程可能用不同参数两次调用同一子蓝图，再测试其中一次的产物。作者需要在运行前看清工具版本、步骤和依赖关系，在运行后确认实际执行位置、失败影响及保留的状态。

## Solution

通过 brw 的蓝图产品入口预览和应用同一份根蓝图。用户组合目标状态、显式动作和其他蓝图；Digby 将其解释为带类型的执行计划。首版以同一份跨平台样例贯通工具选择、Debug 和 Release 构建、Release 产物测试及重跑。

## User Stories

1. 作为蓝图作者，我希望按声明顺序组合步骤，以便后一步使用前一步准备的工具。
2. 作为作者，我希望重复引用同一子蓝图并分别传入必填参数，以便独立运行 Debug 和 Release 构建。
3. 作为作者，我希望按调用位置引用具名输出，以便只测试 Release 的归档。
4. 作为使用者，我希望看到运行时才能确定的值来自哪个调用，以便审阅步骤间的数据传递。
5. 作为作者，我希望自带脚本相对于声明它的蓝图定位，并能指定工作目录，以便从任意目录启动同一流程。
6. 作为作者，我希望命令保留每个参数的边界，并能显式选择解释器，以便可靠处理含空格的路径和管道。
7. 作为使用者，我希望看到平台专属步骤跳过的原因，以及缺少哪项必需能力，以便判断蓝图能否在本机应用。
8. 作为使用者，我希望在首次写入前看到循环引用的完整链和缺参的具体位置，以便直接修正蓝图。
9. 作为作者，我希望知道缺失输出的产出方和使用方，以便修正平台条件或失败的调用。
10. 作为使用者，我希望预览说明哪些状态要在执行时检查，以便识别前序动作可能改变的条件。
11. 作为使用者，我希望重新应用时跳过已满足的变更并重跑选中的动作，以便修正问题后重新测试。
12. 作为维护者，我希望预览和实际报告用同一路径标识每次调用，以便定位第二次构建是否启动或失败。
13. 作为使用者，我希望失败后保留已完成的结果并了解外部命令可能留下的副作用，以便检查现场并重试。
14. 作为作者，我希望按平台锁定工具及其直接、间接软件依赖，以便重现已验证的版本、来源和产物。
15. 作为使用者，我希望普通应用沿用有效锁定记录，缺项或冲突时得到诊断，以便由我决定何时更新版本。
16. 作为使用者，我希望多个版本并存，并能为单个动作选择版本，以便保持现有默认命令入口。
17. 作为作者，我希望声明宿主要求并显式安排修复，以便在依赖步骤前检查实际值并确认修复成功。
18. 作为作者，我希望用外部只读检查和变更动作定义目标状态，以便接入已有 CLI 并区分未满足、查询失败和修复失败。

## Implementation Decisions

- 同一调用的预览与应用遵循同一顺序和定位规则。每次引用独立绑定输入、执行并提供具名输出；步骤可在内部解析依赖。循环引用、缺少必填参数或必需平台能力时，在首次写入前定位报错。
- 平台条件确定产出方会被跳过、而选中步骤需要该输出时，规划报告两处位置与输出名。调用运行后缺少必需输出时，在产出调用处失败。
- 应用到达目标状态时检查现状。预览可运行只读检查；前序动作可能影响结果时，标明“执行时检查”及原因。外部检查默认以 0 表示满足；作者声明表示未满足的退出码，其他退出码或无法启动均为检查错误。未满足才变更，随后复查。
- 直接运行外部命令时保留参数列表；需要 shell 语义时显式指定解释器。引用路径包含每级引用及最终步骤的位置。首次失败停止后续步骤；保留已完成结果，报告已启动命令可能产生的副作用。重新应用从头按序检查与执行。
- 锁定可选。普通应用使用对应平台的锁定记录，缺失或与版本要求不符时首次写入前停止。显式生成或更新记录；本地依赖须能确认匹配才复用。动作所用版本和用户默认入口分别声明。宿主条件单独检查，修复后复查通过才运行依赖步骤。
- 沿用项目的可移植 C 核心和平台实现边界，在相同的用户行为契约下验证各平台。

## Testing Decisions

以用户可调用的 brw 蓝图入口为主验收点。复用现有 CLI 测试中临时目录、测试载荷和落盘检查的做法；Digby 计划行为测试用于定位内核回归。通过参数、工作目录、退出码、产物内容和默认入口验证实际效果。

| 场景 | 通过条件 |
| --- | --- |
| 三平台主场景 | 分别从其他目录启动同一根蓝图。预览核对平台产物、跳过原因、两次调用参数和输出来源，项目产物、安装状态与默认入口保持一致。实际运行核对锁定工具、脚本位置、工作目录、带空格参数和两份构建标记。测试只读到 Release 标记。重跑时已满足目标跳过变更，两次构建与测试再次执行。 |
| 当前平台缺少锁定记录 | 从初始状态单独运行。预览和应用在写入前指出软件、平台与缺项。记录未补齐，构建和测试未启动。 |
| 外部检查错误 | 只声明 3 为未满足。首个检查返回 1 时，两种模式均在同一位置报告退出码，变更和构建均未运行；对照用例返回 3 后执行变更，复查返回 0。 |
| 第二次构建失败 | 从初始状态让 Release 写标记后失败。预览包含两次构建和测试；执行报告定位第二次调用，保留 Debug 产物，核对 Release 标记的实际状态，测试未启动。修正后重跑通过。 |

边界用例覆盖循环引用、缺参、平台能力缺失、两种输出缺失、延后检查、锁定更新与本地依赖匹配、显式切换默认入口、宿主修复与复查、直接传参和显式 shell、检查程序启动失败与复查失败。各平台分别记录系统与架构、构建版本、蓝图及锁定修订、实际命令、退出码、预览与执行报告、最终状态；报告首个偏差或未运行原因。

## Out of Scope

Scoop 兼容工作、读取 Pixi 或 mise 配置格式、为项目环境或工作站预设固定工作流，以及通用插件接口均在首版范围之外。

## Further Notes

设计依据为 ADR 0010。交付判定以已确认的《Digby 与蓝图首版验收清单》为准。编写规格时，Windows、Linux 和 macOS 验收均未运行。
